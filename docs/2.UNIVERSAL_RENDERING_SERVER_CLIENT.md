Dưới đây là bản tổng hợp kiến thức về **Luồng hoạt động Server - Client & Cơ chế Payload** trong Nuxt 3, được chắt lọc dựa trên cách giải thích "bình dân học vụ" dễ hiểu nhất.

# Cơ Chế Universal Rendering: Luồng Server - Client & Payload

Tài liệu giải thích cách Nuxt chuyển dữ liệu từ Server xuống Client để đảm bảo hiệu suất tối đa (tránh gọi API 2 lần).

## 1. Tư Duy Cốt Lõi: Quy Trình "Gửi Phao Thi"

Hãy hình dung quy trình Universal Rendering (SSR + Hydration) như một buổi thi:

- **Server (Giáo Viên):**
  1.  **Giải đề:** Chạy API lấy dữ liệu (`useFetch`).
  2.  **Làm phao:** Viết đáp án vào một tờ giấy nhỏ, gọi là **Payload** (biến `window.__NUXT__`).
  3.  **Giao bài:** Kẹp tờ "phao" này vào bài thi (File HTML) và gửi xuống cho học sinh.
- **Client (Học Sinh):**
  1.  **Nhận bài:** Trình duyệt tải file HTML về.
  2.  **Xem phao:** Mở tờ Payload ra kiểm tra.
  3.  **Chép đáp án:** Lấy dữ liệu từ Payload điền vào bài làm luôn (Hydration).
  4.  **Kết quả:** Không cần tự giải lại (Không cần gọi API lần nữa).

---

## 2. Tại sao `useFetch` lại tìm trong `window.__NUXT__`?

`useFetch` được lập trình để hoạt động một cách "lười biếng" (Lazy) và thông minh nhằm tối ưu tốc độ.

**Logic giả lập bên trong `useFetch`:**

```javascript
function useFetch(url, options) {
  // Bước 1: Kiểm tra xem trong Payload (window.__NUXT__) có dữ liệu tương ứng với key chưa?
  const dataTrongPhao = kiemTraPayload(options.key);

  if (dataTrongPhao) {
    // A. TRƯỜNG HỢP CÓ PHAO (Client Hydration)
    // Lấy dùng luôn, khỏi làm việc vất vả.
    return dataTrongPhao;
  } else {
    // B. TRƯỜNG HỢP KHÔNG CÓ (Server Side hoặc chuyển trang SPA)
    // Đành phải gọi API thật.
    return callApiThat(url);
  }
}
```

> **Mục đích:** Chống **Double Fetch** (Trùng lặp). Nếu Server đã lấy data rồi mà Client lại gọi API lần nữa thì sẽ lãng phí băng thông và làm web chậm.

## 3. Vai Trò Của `Key`: Chìa Khóa Định Danh

Làm sao Client biết lấy cục dữ liệu nào trong đống Payload hỗn độn? Đó là nhờ vào **`key`**.

### Quy trình "Khớp Lệnh" (Matching):

Giả sử bạn viết code:

```typescript
useFetch("/api/products", { key: "products-list" });
```

1.  **Tại Server:**
    - Chạy `useFetch` với key `'products-list'`.
    - Lấy được Data -> Dán nhãn `'products-list'` -> Lưu vào Payload.
    - _Ví dụ:_ `Payload['products-list'] = [Samsung, iPhone...]`

2.  **Tại Client:**
    - Trình duyệt chạy lại dòng code `useFetch(..., { key: 'products-list' })`.
    - Nó cầm chìa khóa `'products-list'` đi tìm trong `window.__NUXT__`.
    - Thấy đúng cái hộp có nhãn `'products-list'` -> Mở ra lấy Data dùng luôn.

### Lưu ý về Key:

- **Tự động:** Nếu bạn không đặt `key`, Nuxt tự sinh ra dựa trên _tên file + dòng code_ (VD: `index-L25`). Server và Client cùng chạy 1 file code nên key tự sinh vẫn khớp nhau.
- **Thủ công:** Bắt buộc đặt `key` khi dùng trong vòng lặp hoặc component tái sử dụng để tránh trùng lặp ID.

## 4. Tóm Tắt Luồng Chạy

| Bước  | Môi trường  | Hành động                   | Kết quả                                   |
| :---- | :---------- | :-------------------------- | :---------------------------------------- |
| **1** | **Server**  | Chạy `useFetch('/api/...')` | Gọi API thật -> Có Data.                  |
| **2** | **Server**  | Serialize Data              | Lưu Data vào `window.__NUXT__` (Payload). |
| **3** | **Network** | Gửi Response                | Gửi HTML + Payload xuống trình duyệt.     |
| **4** | **Client**  | Chạy `useFetch` (Hydration) | **Check Payload trước**.                  |
| **5** | **Client**  | Tìm thấy Key trong Payload  | **Lấy Data dùng luôn** (Không gọi API).   |

Câu hỏi của em chạm đúng vào **"Trái tim"** của Nuxt.js. Hiểu được quy trình này, em sẽ không bao giờ sợ các lỗi như "Hydration Mismatch" hay "Window is undefined" nữa.

Đúng như em nghĩ, chúng ta đang kết hợp SSR (Server-Side Rendering) và CSR (Client-Side Rendering). Thuật ngữ chuyên ngành gọi là **Universal Rendering (hoặc Isomorphic)**.

Anh sẽ mô tả trình tự **từ lúc Build code -> Chạy trên Server -> Xuống Client** một cách trực quan nhất để em hình dung nhé.

---

### 1. Quá trình BUILD (Khi chạy `npm run build`)

Khi em gõ lệnh build, Nuxt (sử dụng Vite bên dưới) sẽ **tách code của em làm 2 bản riêng biệt**:

1. **Server Bundle (`.output/server`):**

- Đây là code sẽ chạy trên Node.js (Nitro).
- Nó **loại bỏ** tất cả những thứ liên quan đến DOM, Window, LocalStorage (vì server không có mấy cái này).
- Nhiệm vụ: Tạo ra chuỗi HTML thô.

2. **Client Bundle (`.output/public`):**

- Đây là các file `.js`, `.css` sẽ được gửi về trình duyệt.
- Chứa đầy đủ logic Vue, sự kiện click, và code xử lý DOM.
- Nhiệm vụ: Làm cho trang web "động đậy" được (Hydration).

---

### 2. Trình tự CHẠY (Runtime Execution Flow)

Hãy tưởng tượng em đang vào trang `/products` và có logic giỏ hàng `useCart` chúng ta vừa viết.

#### GIAI ĐOẠN 1: Tại Server (SSR)

_Khi người dùng gõ URL và Enter._

1. **Server nhận Request.**
2. **Chạy `setup()` (Server-side):**

- Nuxt chạy file `app.vue` -> `layouts/default.vue` -> `pages/products/index.vue`.
- Nó chạy luôn cả composable `useCart()`.
- **Lưu ý:** Lúc này `useState('cart')` được khởi tạo giá trị mặc định là `[]`.
- **Quan trọng:** Nó **BỎ QUA** `onMounted`. (Vì server không thể "mount" vào đâu cả).
- Nó gặp `localStorage`? -> Nếu em không chặn bằng `import.meta.client` (hoặc `onMounted`), server sẽ crash ngay tại đây vì không biết `localStorage` là gì.

3. **Render HTML:**

- Server tạo ra một chuỗi HTML tĩnh: `<div>Giỏ hàng (0)</div>`.
- Server đóng gói `state` hiện tại (cart = []) vào một cái gọi là **Payload**.

4. **Response:** Gửi HTML + Payload về trình duyệt.

#### GIAI ĐOẠN 2: Tại Client (Browser)

_Trình duyệt nhận được HTML._

1. **Hiển thị HTML tĩnh:** Người dùng nhìn thấy trang web ngay lập tức (nhưng chưa bấm được gì). Giỏ hàng hiện số `(0)`.
2. **Download JS:** Trình duyệt tải Client Bundle về.
3. **Hydration (Bơm nước vào bọt biển):**

- Vue khởi động. Nó chạy lại `setup()` một lần nữa (nhưng lần này là ở browser).
- **Khớp State:** `useState` thông minh nhận ra: "À, server có gửi kèm cái Payload cart = [], mình sẽ dùng nó để đồng bộ".

4. **Chạy `onMounted` (Client-side):**

- Lúc này, hàm `onMounted` trong `useCart` mới bắt đầu chạy.
- Nó chọc vào `localStorage` -> Lấy được giỏ hàng cũ (ví dụ 2 item).
- Nó cập nhật `cart.value = [Item A, Item B]`.

5. **Reactivity Update:**

- Vì `cart` thay đổi, Vue tự động update lại giao diện.
- Số trên Header nhảy từ `(0)` -> `(2)`.

---

### 3. Tổng kết vai trò từng phần trong "Vũ trụ" này

Để em dễ nhớ, anh phân tích kỹ từng thành phần code em viết:

#### A. Template (`<template>`)

- **Server:** Được biên dịch thành chuỗi String HTML.
- **Client:** Được biên dịch thành Virtual DOM để Vue so sánh và cập nhật.

#### B. Setup Script (`<script setup>`)

- **Đây là vùng nguy hiểm nhất.** Code trong này chạy **2 lần** (1 lần ở Server, 1 lần ở Client).
- Vì vậy, tuyệt đối không gọi `window`, `document`, `localStorage` trực tiếp ở đây mà không kiểm tra môi trường.

#### C. Composable (`useCart`)

- Cũng chạy 2 lần (nếu được gọi trong setup).
- `useState`: Là cây cầu nối. Dữ liệu khởi tạo ở Server sẽ được "bê" xuống Client thông qua Payload để đảm bảo 2 bên giống nhau.

#### D. `onMounted`

- **Vùng an toàn:** Chỉ chạy 1 lần duy nhất ở Client.
- Nơi lý tưởng để gọi `localStorage`, `setTimeout`, thao tác DOM (`document.getElementById`).

### Tại sao lại cần quá trình phức tạp này?

1. **SEO (Google Search):** Google bot chỉ nhìn thấy Giai đoạn 1 (Server). Nếu làm CSR thuần (như React thường), Google chỉ thấy trang trắng. SSR giúp Google thấy nội dung ngay.
2. **Tốc độ (Performance):** Người dùng thấy nội dung ngay lập tức (First Contentful Paint) mà không phải chờ tải hết file JS nặng nề.
